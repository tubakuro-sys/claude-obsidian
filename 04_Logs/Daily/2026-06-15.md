# 2026-06-15（月）デイリーログ

## 🧩 新規プロジェクト「家族共有アプリ（レシピ・タスク）」構想・技術選定

遠隔地の家族とデータ共有するアプリを、ogawaが作って提供する形で構想。モバイルで相談 → 帰宅後PCで記録。

### 検討の流れ
- データ共有手法を一通り整理：BaaS／表計算間借り／自宅サーバー(NAS)／クラウド自前／P2P
- GitHubでの共有を検討 → Issues/Projectsは「家族もGitHubを使う」前提なら有効。だが「家族は意識せず使う・ogawaが提供」だと、共有トークン管理や利用者識別を自作する手間が出るため不利と判断
- 「無料・アプリで完結・提供する形」の条件で、最初は Firebase + PWA を提案
- 配信は既存の GitHub Pages を維持し、クラウドはデータ層という整理（リリース方式は移行不要）。Web設定キーは公開OK・秘密鍵はコミットしない、が原則
- 容量課金の確認：無料枠は「1日あたりの読み書き回数」＋「ストレージ上限」。無料プランのままなら課金されず頭打ちになるだけ。プロジェクトを分ければ枠は増えるが、家族利用では分ける意味は薄い（ログイン共通・データ共有・管理一元が勝つ）
- 複数家族（自分＋妻）の想定 → プロジェクトは分けず `family_id` で分離＋RLSが定石

### DB選定の転換：NoSQL → SQL（Supabase）
- ogawaは業務で Oracle SQL を使用・テーブル設計可能、アプリ側はClaudeで作る前提
- → 「SQLを覚えなくていい／コードが楽」というNoSQLの利点が薄れる
- レシピ↔材料↔タグ↔家族など関係データ＋集計（買い物リスト等）が多く、SQLが有利
- **Supabase に決定**。RLS で家族分離が綺麗、PostgreSQLで移植性も高い
- 難点「7日無アクセスで自動停止」は GitHub Actions の定期pingで回避
- Oracle→Postgres の方言差は小さい（DUAL不要・SYSDATE→now()・NVL→COALESCE・ROWNUM→LIMIT 等）。Oracle CloudでOracle DB無料も技術的には可能だが、家族アプリにはSupabaseの方が楽（API・認証・RLSが付属）

### 参考アプリ：CookGo
- AIでURL/動画からレシピ取り込み、タグ整理、献立自動、買い物リスト自動、分量スケーリング
- 機能が関係データ＋集計中心 → SQL採用を後押し
- AI取り込みは大きな別機能 → フェーズ3へ。まずは登録・共有・タグ検索（フェーズ1）から

### 写真対応の容量懸念
- テキストは無視できるが、写真が容量の主役
- 「データ」と「写真」を分離：写真はオブジェクトストレージに置き、DBにはURLだけ持つ
- **Cloudflare R2**（10GB無料・egress無料・カード不要・期限なし）が最適。1MB写真で約1万枚
- 足りない／家に置きたいなら nas001 に置き Cloudflare Tunnel で配信（NASの本領）
- アップロード時に縮小・圧縮（1024px/WebP）で容量寿命を延ばす

### 開発ツール・モデル方針
- 設計・相談はチャット（Opus 4.8思考）、実装は **Claude Code** が適任（複数ファイル＋git＋コマンド実行）
- Claude Code は Sonnet 4.6 を主力、難所だけ Opus 4.8 → 質と使用量のバランス
- 生成物（特にRLS／キー）は目視確認。エージェントは誤った方向に進むことがある
